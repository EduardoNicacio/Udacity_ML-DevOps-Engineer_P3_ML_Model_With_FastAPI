# Instructions

## Before You Start

Review the [project rubric](https://learn.udacity.com/rubric/5033) before you begin so that you understand what will be evaluated. Choose either the GitHub or Azure DevOps workflow and use it consistently throughout the project.

## Repository and Continuous Integration

### Option A: GitHub and GitHub Actions

1. Create a directory for the project and initialize Git, or fork or clone the [project starter repository](https://github.com/udacity/nd0821-c3-starter-code).
2. Connect the local repository to your GitHub repository.
3. Commit and push your work regularly using meaningful commit messages. Commit any trained model that is required to run or evaluate the project.
4. Configure GitHub Actions to run both `pytest` and `flake8` when code is pushed to `main` or `master`.
5. Use the same Python version in GitHub Actions that you used during development. Both `pytest` and `flake8` must pass without errors.

### Option B: Azure Repos and Azure Pipelines

1. Create or open the private Azure DevOps project in which you will store your work.
2. Import the following public starter repository into Azure Repos:

    ```bash
    text   https://github.com/udacity/nd0821-c3-starter-code  
    ```

3. Copy the clone URL displayed by Azure Repos and clone the imported repository:

    ```bash
    bash   git clone https://dev.azure.com/<organization>/<project>/_git/<repository>   cd <repository>   git remote -v  
    ```

4. Commit and push your work regularly using meaningful commit messages. Normal commands such as `git add`, `git commit`, `git pull`, and `git push` do not change when the remote is Azure Repos. Commit any trained model that is required to run or evaluate the project.
5. Add an `azure-pipelines.yml` file that installs the project dependencies and runs both `pytest` and `flake8` on pushes to the protected main branch. Use the same Python version that you used during development. Both checks must pass without errors.
6. Configure the pipeline as a required **Build validation** policy for pull requests targeting `main`. In Azure Repos, required pull-request validation is configured through the target branch's policies rather than relying only on a `pr:` trigger in the YAML file.

For repository import, authentication, branch policies, Azure Pipeline examples, and deployment options, follow the **GitHub to Azure DevOps Translation Guide** earlier in this course. Follow your organization's security and data-handling policies. Never commit a personal access token, password, API key, deploy hook, or other credential.

## Project Directory

Use the directory containing `setup.py` and `main.py` as the project root: the repository root in the flattened layout, or `starter/` in older copies. Run installation, training, tests, and deployment commands there. The `starter/` subdirectory is the Python package. Install it with `python -m pip install -e .` after installing `requirements.txt`.

## Data

The data is located at `data/census.csv`, relative to the project root. Information about the dataset is available from the [UCI Machine Learning Repository](https://archive.ics.uci.edu/ml/datasets/census+income).

The data contains spaces that interfere with processing. Open the file in pandas to observe the problem, and then use a text editor or another appropriate method to remove the spaces. Do not otherwise rename or modify the CSV columns merely to accommodate Python variable naming rules.

## Model

Using the starter code:

1. Write a machine learning model that trains on the cleaned data and saves the trained model. Complete every function that has been started.
2. Write unit tests for at least three functions in the model code.
3. Write a function that outputs the model's performance on slices of the data. For simplicity, you may evaluate slices of the categorical features.
4. Write a model card using the provided template.

### Required Model Artifacts

Include the final trained model and all fitted preprocessing artifacts needed for inference (such as an encoder or label binarizer) in your submission, whether saved as `.pkl`, `.joblib`, or an equivalent format. The reviewer must be able to run inference without retraining.

The starter `.gitignore` intentionally excludes generated models. Keep these rules and explicitly stage each required final artifact with `git add -f <path-to-required-artifact>`, replacing the placeholder with its actual path. Review the staged files, then commit and push them; do not force-add the entire directory.

## API Creation

Create a RESTful API using FastAPI. The API must implement:

- a `GET` request on the root path that returns a welcome message;
- a `POST` request that performs model inference;
- type hints; and
- a Pydantic model that ingests the `POST` request body and includes example values.

The dataset has column names containing hyphens, which cannot be used directly as Python variable names. Do not modify the column names in the CSV. Instead, use FastAPI or Pydantic functionality such as field aliases to map the request fields correctly.

Write three unit tests for the API:

- one test for the `GET` endpoint;
- one `POST` test that produces one possible prediction; and
- one `POST` test that produces the other possible prediction.

Run the sanity check from the project root:

```bash
python sanitycheck.py
```

The script scans the tests written for the `GET` and `POST` endpoints and reports common problems. Fix any reported issues and run the script again. Because the script uses heuristics, it can occasionally miss a problem or report a false positive. Always compare the implementation with the project rubric as the final source of requirements.

## API Deployment to a Cloud Application Platform

Create an account with a cloud application platform such as Render or Heroku. Heroku no longer provides its former free-tier plan, so charges might apply. You may use another cloud application platform if it satisfies all rubric requirements.

Deploy only the tested code from the protected `main` branch, and configure continuous deployment so that deployment occurs only after continuous integration succeeds.

### GitHub Deployment Workflow

Configure the cloud platform or your GitHub Actions workflow to deploy the application from the GitHub repository after the required tests and lint checks pass. Enable automatic deployment from the protected branch.

### Azure DevOps Deployment Workflow

Add a deployment stage to `azure-pipelines.yml`. The deployment stage must:

- depend on the successful test stage;
- run only for the protected `main` branch; and
- retrieve deployment credentials from authorized secret variables or a restricted variable group.

For Render, you may store the service's complete deploy-hook URL as a secret variable such as `RENDER_DEPLOY_HOOK_URL` and call that hook from the deployment stage. For Heroku, you may store the account email and app name as variables, store the API key as a secret variable, and push the tested commit to the Heroku Git remote. The Heroku remote is a deployment destination; Azure Repos remains the source repository.

Follow any approval, service-connection, or self-hosted-agent requirements imposed by your organization. Do not bypass organizational controls, and do not store deployment credentials in source files or pipeline YAML.

Regardless of the platform workflow you choose:

1. Account for path differences between the local and hosted environments.
2. Run `flake8` and the tests locally before pushing changes when possible.
3. Write a script that uses the `requests` module to make one `POST` request to the live API and prints both the inference result and the HTTP status code.
